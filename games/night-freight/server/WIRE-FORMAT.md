# Night Freight wire format

This document is the contract between the Rust game component and the browser
client. Everything below is the JSON that the participant client receives as
`snapshot.view` (the role view), `snapshot.completion` and sends through
`snapshot.act(action)`. All shapes come from serde types in `server/src`; the
examples under `server/examples/` and quoted below are generated by the test
`tests/wire_examples.rs` from the real game, so they cannot drift.

## Conventions

- Object keys are `snake_case`. Enum values are `snake_case` strings.
- Enums with data are **internally tagged**: `{"type": "<variant>", ...fields}`
  (the tag is `type`; the sole exception is a disruption effect in scenario
  files, which never reaches the client).
- Optional values are `null` when absent; keys are never omitted.
- Hours are integers from 0 to 24. Hour 0 is midnight; the horizon is 24.
- Identifiers: engines `"E1"`, `"E2"`, ...; stations lower-case slugs
  (`"avon"`, `"bath"`, `"corning"`, `"dansville"`, `"elmira"`); orders `"O1"`, ...;
  cars are small integers (lower ids are chosen first by the simulator).
- Role names are `"freight"` and `"routing"`. Which Parlando seat plays
  Freight is configuration (`freight_seat`, default `a`); the view's `role`
  field tells the client which one it is.

## Configuration

```json
{ "scenarios": ["tutorial", "corning-juice", "bath-bananas"], "freight_seat": "a", "max_runs": 6 }
```

All three keys are optional (`{}` is valid). `max_runs` is the number of joint
runs allowed per scenario, both acts together.

## Actions (client to server)

Every action is an object with a `type`. Examples of every variant are in
`examples/actions.json`.

| `type` | Fields | Meaning |
| --- | --- | --- |
| `edit` | `edit`: a note edit (below) | Edit the actor's own notes. Only in phase `planning`. Clears the actor's `ready`. |
| `set_ready` | `ready`: bool | Declare or withdraw readiness. Only in `planning`. When both are ready the run starts and the phase becomes `replaying`. |
| `replay_finished` | none | The actor has watched the replay. Only in `replaying`, once per role. |
| `continue` | none | The actor has seen the scenario result. Only in `scenario_done`, once per role. |

### Note edits (`edit.edit`)

All indices are zero-based. `stop` is an index into the engine's strip.

| `type` | Fields |
| --- | --- |
| `append_stop` | `engine`, `station` (must be adjacent to the strip's last station) |
| `truncate_stops` | `engine`, `from` (removes stops `from..`; `from >= 1`) |
| `set_depart` | `engine`, `stop`, `depart` (a Depart, below) |
| `insert_op` | `engine`, `stop`, `index` (`0..=len`), `op` (an Op, below) |
| `remove_op` | `engine`, `stop`, `index` |
| `set_heard_arrival` | `engine`, `stop`, `hour` (int or `null` to clear) |

```json
{ "type": "edit", "edit": { "type": "append_stop", "engine": "E1", "station": "dansville" } }
{ "type": "edit", "edit": { "type": "set_depart", "engine": "E2", "stop": 1,
    "depart": { "type": "after", "engine": "E1", "plus_hours": 1 } } }
{ "type": "set_ready", "ready": true }
{ "type": "replay_finished" }
{ "type": "continue" }
```

### Rejections

A rejected action leaves the state unchanged and returns one of these codes
(the participant client surfaces it through the usual rejection channel):

| Code | Reason |
| --- | --- |
| `wrong_phase` | The action is not allowed in the current phase. |
| `unknown_engine` | An engine id (also inside `after`) does not exist. |
| `unknown_station` | A station id does not exist. |
| `unknown_order` | A `deliver` op names an order that does not exist. Checked **only for Freight**; Routing may write any order id (they do not know the orders). |
| `not_adjacent` | `append_stop` to a station without a direct edge. |
| `index_out_of_range` | `stop`/`index`/`from` outside the list. |
| `fixed_stop` | `truncate_stops` with `from = 0`. The first stop is the engine's current station. |
| `too_many_stops` | More than 12 stops in one strip. |
| `too_many_ops` | More than 6 ops at one stop. |
| `invalid_count` | An op `count` outside 1 to 9. |
| `incompatible_load` | A `couple`/`uncouple` op whose `load` is `loaded` with a commodity the car `kind` cannot carry (juice in a boxcar, oranges or bananas in a tanker). |
| `invalid_hour` | A depart/heard hour above 24. |
| `no_change` | The edit changes nothing, `set_ready` repeats the current value, or `replay_finished`/`continue` is sent twice by one role. |

Edits are validated only against facts both roles share. A step that cannot
work (coupling a car that is not there) is accepted and fails in the run.

**Important for the client.** Parlando delivers every accepted action to
both roles. The partner's `edit` actions therefore arrive in your browser; the
client must ignore them. Only the view is authoritative, and it never contains
the partner's notes.

## Plan, Stop, Depart, Op

A **Plan** is the notes of one role:

```json
{ "engines": { "E1": [ Stop, Stop, ... ], "E2": [ ... ] } }
```

Every engine is always present. `engines[id][0]` is the engine's current
station (it cannot be removed). Consecutive stops are adjacent on the map.

**Stop**

```json
{ "station": "corning", "depart": Depart, "ops": [Op, ...], "heard_arrival": 4 }
```

- `depart` is owned by Routing, `ops` by Freight; each player can edit all
  fields of their own notes, but only the owner's field of the two notes is
  used in the joint run. The rest is their belief about the partner (draw it
  dashed). `heard_arrival` is an annotation with no effect (int or `null`).

**Depart**

| JSON | Meaning |
| --- | --- |
| `{"type":"immediately"}` | Leave in the hour of arrival. |
| `{"type":"at","hour":5}` | Leave when the clock is at or past hour 5. |
| `{"type":"after","engine":"E1","plus_hours":1}` | Leave `plus_hours` after engine E1 is first present at this station (at or after this engine's arrival). Never leaves if E1 never comes. |

**Op** (an engine runs one op at a time and, whenever it is free, starts the
**first op in the list whose precondition holds now**; list order only breaks
ties. See "Stop semantics" below.)

| JSON | Effect |
| --- | --- |
| `{"type":"couple","kind":"boxcar","load":{"type":"any"},"count":2}` | Couple `count` cars of `kind` (`boxcar`/`tanker`) matching the `load` filter from the yard. |
| `{"type":"uncouple","kind":"boxcar","load":{"type":"loaded","commodity":"oranges"},"count":1}` | Uncouple matching cars into the yard. |
| `{"type":"load","commodity":"oranges","count":2}` | Load `count` empty compatible cars on the engine from the station's stock. Takes `load_hours`. |
| `{"type":"process","count":1}` | Run `count` loaded input cars and `count` empty output cars through the station's factory. |
| `{"type":"deliver","order":"O1"}` | Deliver loaded cars against the order at its destination (as many as the order still needs, at least one). |

**LoadFilter** (the `load` field of `couple` and `uncouple`)

| JSON | Matches |
| --- | --- |
| `{"type":"any"}` | Every car of the kind. **The default**: a missing `load` field means `any`. Empty cars are taken first, then the lowest car id. |
| `{"type":"empty"}` | Only empty cars. |
| `{"type":"loaded","commodity":"oranges"}` | Only cars loaded with that commodity (`oranges`, `bananas`, `juice`). The commodity must fit the car `kind` (`incompatible_load` otherwise). |

`load: null` and bare commodity strings are no longer accepted for `couple`
and `uncouple`. The `load` of a car in the view is still `null` or a commodity.

**Stop semantics**

1. *Departure comes last.* An engine never leaves a stop while one of its ops
   there is in progress, and never while an op there could still start. When
   the depart condition holds it finishes the op in progress, starts every
   remaining op that is possible (zero-duration ops chain within the hour),
   and leaves only when no remaining op can start. Ops still unexecuted at
   that moment produce one `op_abandoned` event each, carrying a `reason`.
2. *Retry.* Before the depart condition holds, ops that are not yet possible
   are retried every hour (so a hand-over from another engine works with
   `at` or `after`). With `immediately` and nothing possible the engine
   leaves at once.
3. *Hold.* An engine blocked by a signal or closed edge keeps working its ops
   while it waits; unexecuted ops are abandoned only when it enters the edge.
4. *Last stop.* An engine at its last stop (or one that never leaves) keeps
   retrying; ops still unexecuted at the end of the run are reported with
   `op_abandoned` at `end_hour`.

## The view

`snapshot.view` for one role, with the fields in the table. Generated examples
follow the table.

| Field | Type | Notes |
| --- | --- | --- |
| `role` | `"freight"` or `"routing"` | The viewer. |
| `phase` | `"planning"`, `"replaying"`, `"scenario_done"`, `"finished"` | |
| `act` | 1 or 2 | 2 after a disruption. |
| `scenario_index`, `scenario_count` | int | 0-based index. |
| `scenario_id`, `scenario_title`, `scenario_summary` | string | |
| `runs_used`, `max_runs` | int | Runs count both acts. |
| `map` | Map | Shared. |
| `briefing` | Briefing | The viewer's private facts only. |
| `notes` | Plan | The viewer's own notes only. |
| `ready`, `replay_finished`, `continue` | `{"me": bool, "partner": bool}` | `ready` is cleared when a run ends. |
| `last_run` | LastRun or `null` | Present from the first run on, also after a reload. |
| `scores` | list of Score | Finished scenarios (including the current one in `scenario_done`/`finished`). |

### Map (shared)

```json
{
  "stations": [{ "id": "elmira", "name": "Elmira", "factory": true }],
  "edges":    [{ "a": "avon", "b": "dansville" }],
  "engines":  [{ "id": "E1", "station": "corning", "failed": false, "available_from": null }],
  "horizon": 24,
  "start_hour": 0
}
```

- Edges have **no travel times** (Routing's fact).
- `engines[].station` is the station where each engine stands at the start of
  the current act; in act 2 it is the position at the disruption hour.
  `failed` is public (the film showed it). `available_from` is an hour in
  Routing's view and `null` in Freight's view.
- `start_hour` is later than the scenario start in act 2.

### Briefing

Freight (`type: "freight"`):

```json
{ "type": "freight",
  "orders": [OrderState], "cars": [Car],
  "stock": [{ "station": "avon", "commodities": ["bananas"] }],
  "factories": [{ "station": "elmira", "input": "oranges", "output": "juice", "hours": 1 }],
  "load_hours": 1, "deliver_hours": 0,
  "announcement": Announcement | null }
```

Routing (`type: "routing"`):

```json
{ "type": "routing",
  "travel_times": [{ "a": "avon", "b": "dansville", "hours": 3 }],
  "restrictions": [{ "a": "avon", "b": "bath", "from_hour": 5, "until_hour": 9 }],
  "capacities": [{ "engine": "E1", "capacity": 3 }],
  "announcement": Announcement | null }
```

`restrictions` are closure windows: an engine cannot **enter** the edge in
hours `from_hour <= h < until_hour`. A track closure after a disruption has
`until_hour: 25`.

`OrderState`: `{ "id", "commodity", "count", "to", "deadline", "delivered", "delivered_at" }`.
`Car`: `{ "id": 3, "kind": "boxcar", "load": null | "oranges", "at": CarAt }` with
`CarAt` = `{"type":"yard","station":"corning"}` or `{"type":"coupled","engine":"E1"}`.

`Announcement` (only in act 2, and only for the role the disruption concerns;
the other role has `null` and must be told by their partner). Every variant has
a plain-language `message`:

```json
{ "type": "engine_failure", "engine": "E2", "station": "elmira", "hour": 7, "message": "..." }   // Routing
{ "type": "track_closure", "a": "avon", "b": "dansville", "from_hour": 7, "message": "..." }      // Routing
{ "type": "late_order", "order": { "id": "O3", "commodity": "bananas", "count": 1, "to": "corning", "deadline": 18 },
  "deadline_changes": [{ "order": "O2", "deadline": 12 }], "hour": 5, "message": "..." }           // Freight
```

### LastRun

```json
{
  "number": 1, "act": 1,
  "success": false,
  "interrupted_at": null,
  "actual": Trace,
  "expected": Trace,
  "divergence": Divergence | null,
  "orders": [OrderOutcome]
}
```

- `actual` is what really happened (Routing's route plus Freight's ops).
  `expected` is what the **viewer's own notes** predicted on their own (the
  ghost). The two roles receive the same `actual` and different `expected`.
- `success` is true only for a run in which every order was met **and** which
  was shown to the end. It is false for an interrupted run.
- `interrupted_at` is the disruption hour when the run was cut short. Both
  traces end at that hour (see "Cut traces"), and `actual` ends with a
  `disrupted` event. The client plays the film up to that event, shows the
  disruption, then waits for `replay_finished` handling as usual.
- `orders` are the standings at the end of `actual` (same as `actual.orders`).
- A run that succeeds in act 2 has `success: true`, `act: 2`.
- After a disruption the `last_run` of the interrupted run stays in the view
  during act-2 planning until the next run replaces it.

**Trace**

```json
{ "initial": WorldSnapshot, "events": [Event], "end_hour": 14, "orders": [OrderOutcome], "success": true }
```

- `initial` is the whole world at the start hour; `events` are in chronological
  order; every event has an `hour`. `end_hour` is the last simulated hour (it
  is 24 when some engine kept waiting; order-missed events can lie beyond the
  last engine event).
- To animate, start from `initial` and apply the events. Between events nothing
  changes. An engine that has `depart`ed is on the edge until its
  `arrive_hour`.

**WorldSnapshot**

```json
{ "hour": 0,
  "engines": [{ "id": "E1", "station": "avon", "capacity": 3, "available_from": 0, "arrived_at": 0, "failed": false }],
  "cars": [Car],
  "orders": [OrderState] }
```

**Event**: `{ "hour": 7, "kind": { "type": ..., ... } }` with these kinds:

| `type` | Fields | Notes |
| --- | --- | --- |
| `arrive` | `engine`, `station`, `stop` | `stop` is the index of the reached stop in the engine's strip. |
| `depart` | `engine`, `from`, `to`, `stop`, `arrive_hour` | `stop` is the index of the stop being left. The engine occupies the single-track edge from this hour up to (not including) `arrive_hour`. |
| `hold` | `engine`, `station`, `reason` (`"signal"` or `"closed"`) | The engine wants to leave but is held; emitted once per blockage (and again if the reason changes). The depart event follows when it can go. Show a red signal. |
| `op_started` | `engine`, `station`, `stop`, `index`, `op`, `finish_hour` | Only for ops with a duration (`load`, `process`, and `deliver` when `deliver_hours` > 0). The op takes effect, with an `op_done`, at `finish_hour`; the engine is busy meanwhile and does not leave. |
| `op_done` | `engine`, `station`, `stop`, `index`, `op`, `cars` | `cars` are the car ids affected (for `process`: input cars then output cars). Zero-duration ops produce only `op_done`. |
| `op_abandoned` | `engine`, `station`, `stop`, `index`, `op`, `reason` | The op never became possible while the engine stood there, so it was not executed. Emitted when the engine leaves the stop (or at `end_hour` for an engine that never leaves). `reason` is a FailReason, below. |
| `op_unreached` | `engine`, `station`, `visit`, `index`, `op` | Freight op for a visit that Routing's route does not contain; emitted at the start hour. |
| `order_met` | `order` | Delivered completely at or before the deadline. |
| `order_missed` | `order`, `why` | Still undelivered at the deadline hour. `why` is a MissReason, below. |
| `disrupted` | `what` | Only at the end of an interrupted `actual` trace; see below. |

`index` is the position of the op in its stop's `ops` list; `stop` is the
stop index in the engine's strip.

**FailReason** (`op_abandoned.reason`). `CarCount` is
`{ "load": null | "oranges" | ..., "count": 1 }`; `kind` is `boxcar`/`tanker`;
`load` in the first two reasons is a LoadFilter.

| `type` | Extra fields | Meaning |
| --- | --- | --- |
| `no_matching_cars_in_yard` | `kind`, `load`, `wanted`, `found`, `yard` | `couple`: the yard has `found` matching cars, not `wanted`. `yard` lists the yard's cars of that kind by load (`[CarCount]`, empty cars first), e.g. "the yard has 1 empty boxcar". |
| `over_capacity` | `wanted`, `carried`, `capacity` | `couple`: the cars exist but exceed the engine's capacity. |
| `no_matching_cars_on_engine` | `kind`, `load`, `wanted`, `found`, `coupled` | `uncouple`: the engine carries `found` matching cars; `coupled` lists its cars of that kind by load. |
| `no_stock_here` | `commodity` | `load`: the station does not stock the commodity. |
| `no_empty_cars_on_engine` | `kind`, `wanted`, `found` | `load`/`process`: too few empty cars of the kind the op needs. |
| `no_factory_here` | none | `process` at a station without a factory. |
| `no_input_cars` | `load`, `wanted`, `found` | `process`: too few cars loaded with the factory's input. |
| `wrong_destination` | `order`, `to` | `deliver`: the order is destined for station `to`. |
| `no_order_loads_on_engine` | `order`, `commodity`, `coupled` | `deliver`: no car loaded with the order's commodity; `coupled` lists everything the engine carries by load. |
| `order_filled` | `order` | `deliver`: the order is already complete. |
| `unknown_order` | `order` | `deliver`: no such order in this world. |

Unreached ops keep their own event (`op_unreached`). When several preconditions
fail, the first in this order is reported: yard cars before capacity (couple),
stock before empty cars (load), factory, input, then empty output cars
(process), order, destination, then loads (deliver).

**MissReason** (`order_missed.why`), decided from the whole trace, so a car
that arrives after the deadline is still named.

| `type` | Fields | Sentence |
| --- | --- | --- |
| `no_car_reached` | `commodity`, `to` | "No car of oranges reached Dansville." |
| `reached_after_deadline` | `commodity`, `to`, `reached_at`, `deadline` | "A car of oranges reached Dansville at 7, after the 5 deadline." |
| `reached_not_delivered` | `commodity`, `to`, `reached_at`, `delivered`, `count` | "A loaded car reached Dansville but was never delivered." (`delivered` of `count` car loads were.) |
| `delivered_after_deadline` | `commodity`, `to`, `delivered_at`, `deadline` | The order was completed, but late. |

"Reached" means a car loaded with the commodity stood at the destination, in
the yard or on a standing engine. The first applicable row wins, top to bottom
in this order: `delivered_after_deadline`, `no_car_reached`,
`reached_after_deadline`, `reached_not_delivered`.

**Disruption notice** (`disrupted.what`, public to both roles):

```json
{ "type": "engine_failure", "engine": "E2", "station": "elmira" }
{ "type": "track_closure", "a": "avon", "b": "dansville" }
{ "type": "late_order" }
```

The film shows the failure (smoking engine), the closure (red signals on the
line) or a telegram arriving at the depot. The details are in the private
`announcement`.

**Divergence**: the earliest point at which `actual` and `expected` differ for
some engine.

```json
{ "hour": 0, "engine": "E1", "actual": Event | null, "expected": Event | null }
```

One of `actual`/`expected` is `null` when one trace has no further event for
that engine. `divergence` is `null` when the two traces agree.

**OrderOutcome**: `{ "id", "commodity", "count", "to", "deadline", "delivered", "delivered_at", "met" }`.

### Cut traces

When a run is interrupted at hour `h`, `actual` and `expected` contain every
event up to and including the hour-`h` arrivals and operation completions, but
nothing of hour `h`'s departures or later. The play-back therefore stops with
the disruption. `end_hour` equals `h`.

### Score and completion

`scores[]` and `completion.scores[]` use the same object:

```json
{ "scenario": "corning-juice", "orders_met": 3, "orders_total": 3, "runs_used": 2, "replanned": true }
```

`orders_met`/`orders_total` come from the last run of the scenario
(`orders_total` includes a late order). `replanned` is true when a run
succeeded after a disruption. The completion value is `{ "scores": [Score] }`.

## Phases and what the client does

```
planning {act 1}  --both ready-->  replaying
replaying         --both replay_finished-->
    planning {same act}     the run failed and runs remain
    planning {act 2}        the run was interrupted (new world, notes replaced)
    scenario_done           the run succeeded, or the run budget is used up
scenario_done     --both continue--> planning of the next scenario, or finished
```

- On entering `replaying`, `last_run` holds the run to play. Play `actual`
  with the viewer's `expected` as ghost, then send `replay_finished` (for a
  failed run, once the failure has been shown and the player presses "Back to
  planning").
- After `replay_finished` of both roles the phase changes; `ready` and
  `replay_finished` are cleared. Reloading during `replaying` or `planning`
  restores everything from the view.
- If the run succeeded while the budget is not exhausted and a disruption
  candidate applies, the run is cut at the disruption hour (`interrupted_at`),
  and the next planning phase is act 2.
- If a success uses the last permitted run, no disruption happens: the whole
  day is shown and the scenario ends.
- In act 2 both players' notes are replaced by the remainder of the merged
  plan that was running. `stops[0]` of each engine is then the position at the
  disruption hour (an engine that was on the track appears at its destination
  and is available from its arrival hour). Ops already executed are gone from
  the notes. The world in the `map` and the briefing is the state at the
  disruption hour. Orders already delivered have `delivered_at` set.
- The completion value appears after both roles `continue` past the last
  scenario (`phase: "finished"`).

## Information boundary

A view never contains the partner's notes or the partner's briefing. A
role learns shared facts only through the replay (the traces carry the whole
world: travel times via `depart`/`arrive_hour`, cars, orders, capacities in
`initial`), exactly as the film shows them. `briefing` never changes role.

## Analysis metadata (researchers, not sent to participants)

On each accepted `edit`: `{"type":"edit","actor":"routing","agreement":0.4}`
(fraction of stops and ops identical by visit key across the two notes). On
each run: `{"type":"run", number, act, freight_notes, routing_notes, merged,
unreached, actual, expected_freight, expected_routing, divergence_freight,
divergence_routing, agreement, interrupted_at, disruption}` (see
`examples/analysis-run.json`). `actual` and the expectations are
`{success, orders_met, orders_total, end_hour}` for the full, uncut runs.
